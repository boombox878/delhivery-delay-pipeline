# Delhivery Last-Mile Delay Intelligence Pipeline



Capstone project, Artificial Intelligence and Machine Learning Certification Program, E\&ICT Academy, IIT Roorkee.

Everything runs offline on free libraries (pandas, NumPy, scikit-learn, joblib). The data is synthetic, produced by `generate\_data.py`; Delhivery's real records are not used. Money is in Indian Rupees (INR).



The repository answers three questions in one connected pipeline: how long will a parcel take (Part B), which parcels will miss their promise (Part C), and which hubs need which playbook (Part D). Part A prepares the data for all of them. The cleaning and feature functions live once in `src/shipment\_prep.py` and are reused by Part A and by the scoring script.



## How to run



From a fresh clone of the `main` branch (Python 3.11 or newer):



```bash

# 1. Install the pinned dependencies fully offline

pip install -r requirements.txt



# 2. Generate the synthetic shipments and hub data tables

python generate_data.py #prints- 24 1224 48



# 3. Clean the raw tables and construct the base features

python part_a_clean_eda.py



# 4. Train and cross-validate the point-estimate regression models

python part_b_regression.py



# 5. Build the stratified delay classifier and find the risk alerts threshold

python part_c_classification.py



# 6. Execute K-Means clustering to extract operational hub segments

python part_d_segments.py



# 7. Package and serialize the winning models into deployment assets

python package_model.py



# 8. Score the unlabelled new shipments batch and assign actions list

python predict_delay.py
```



The scripts must be run in this order because each one reads files written by an earlier one. `models/delay\_model.pkl` is regenerated by running `python package\_model.py`. The committed pickle loads reliably only on the scikit-learn version pinned in `requirements.txt` (scikit-learn 1.8.0); if your installed versions differ, re-run `package_model.py` instead of loading the committed pickle. Every random step uses `random\_state=42` (the data generator uses its own fixed seeds), so repeated runs give the same files; running `predict_delay.py` twice gives byte-identical output.



## Data findings

Based on the exploratory data analysis executed across the historical records, the following key insights were uncovered:

* **Highest Risk Service Type:** The `Express` service tier suffers the highest delay frequency, experiencing a delay rate of **0.4897** (where 119 out of 243 shipments missed their promised delivery time window).

* **Delay Progression by Hub Tier:** Structural delays increase significantly as we descend the infrastructure tiers. Tier 1 hubs maintain a low delay rate of **0.0400**, which increases to **0.2150** for Tier 2 hubs, and escalates severely to **0.4400** for Tier 3 hubs.

* **Impact of Transit Distance Bands:** Transit distance exhibits a strong compounding relationship with package drops. The delay rate maps out as follows:

 *0–200 km**: 0.0219
 *201–400 km**: 0.1368
 *401–600 km**: 0.4364
 *601+ km**: 0.8523

* **Top 3 Drivers of Delivery Duration:** Sorting the absolute correlation values against `delivery_hours` reveals that the top three predictive signals are:

*1. `promised_hours`: **0.8370**

*2. `distance_km`: **0.4010**

*3. `n_stops`: **+0.3247**

* **Reason for Log-Transforming Declared Value:** The raw distribution of parcel values is highly right-skewed due to an exponential lognormal generation process, resulting in a large gap between the median filled value of **INR 1,121.50** and its arithmetic mean of **INR 1,533.05**. Transforming this column into `log_declared_value` successfully normalises the scale (bringing the mean to **7.0280** and the median to **7.0220**), which prevents large-value packages from destabilising the model weight updates.



Data cleaning in numbers (from `part_a_checks.csv`): 36 missing distances, 24 missing weights plus 5 sentinel weights (999 kg, treated as missing), 12 missing declared values and 18 missing payment modes were filled or labelled; 12 messy service-type spellings collapsed to 3. After the hub merge there are still 1,200 rows and 0 missing cells across the 17 features, `delivery_hours` and `is_delayed`.



## 3. Model Results (Regression)

Split: 840 training, 180 validation, 180 test rows. The scaler was fitted on training rows only: the scaled training columns have a largest absolute mean of about 4e-16 (shown as 0.0 after rounding to 4 places), while the scaled test rows give 0.2187 (`part_b_checks.csv`), which proves the scaler did not see the test rows.





* **Baseline Performance:** Predicting the simple global mean of the training target across all validation rows yields an $R^2$ score of **-0.0210**. This negative score confirms that a naive baseline possesses zero predictive power and performs worse than the true data mean.



* **Winning Regression Model:**Linear regression, with validation RMSE 4.8912 hours (R² 0.9313). Gradient boosting was almost identical (RMSE 4.9165, R² 0.9306), then random forest (5.5095, R² 0.9128) and the decision tree (6.2796, R² 0.8867).



* **Tree-Depth Diagnostics (Bias vs. Variance):**Depth 1 is high bias: train RMSE 11.6334 and validation RMSE 12.1324 are both large and close (gap 0.4990), and depth 2 is similar (10.4114 versus 9.3687). Depths 12 and unlimited are high variance: unlimited depth fits the training set perfectly (train RMSE 0.0) but validation RMSE is 7.8368, a gap of 7.8368 hours; depth 12 has a gap of 5.9927. Validation error is lowest at depth 6 (RMSE 6.2796, gap 1.5682), which is the depth used for the decision tree. Depth 6 is 5.8528 hours better than depth 1.



* **Learning-Rate Spectrum Analysis:\*\* A learning rate of \*\*0.1\*\* proved optimal. Lower learning rates (0.01) fail because the gradient updates move too slowly within 100 estimators, whereas higher learning rates (1.0) cause the optimization to overshoot the local minima, resulting in degraded validation performance.



* **Cross-validation (`part_b_cv.csv`, same `KFold(5, shuffle=True, random_state=42)` for both).** Gradient boosting: mean R² 0.9353 (std 0.0045). Linear regression: mean R² 0.9261 (std 0.0048). The cross-validated ranking disagrees with the validation ranking, because on validation linear regression was better by only 0.0253 hours of RMSE. The five-fold estimate uses all 1,020 rows and is far less affected by which 180 rows happened to be in validation, and the data contains interactions a straight line cannot represent (the sale window adds 12 extra hours to Express parcels and rain adds 8 extra hours on lanes over 400 km). gradient boosting prefered

* **Test result\*\* By the pre-stated rule (lowest validation RMSE), the final model scored once on the test rows is linear regression: RMSE 4.5235 hours, MAE 3.5671 hours, R² 0.9493. I did not re-score gradient boosting on the test rows, so the test set stays untouched by the shipping decision









## Model Results (Classification)

Stratified split gives 840 / 180 / 180 rows with 195 / 42 / 41 delayed parcel



* **Uselessness of Blind Baseline:** Predicting "not delayed" for every parcel has validation accuracy 0.7667 (TN 138, FN 42) but recall 0: it catches none of the 42 delayed parcels, so it is useless for the operations goal even though the accuracy looks decent. The trained models have accuracy 0.8833 to 0.9056 (`part_c_models.csv`) with F1 of 0.8046 (logistic regression), 0.7470 (decision tree, depth 6) and 0.7848 (default forest).



* **Feature Importance vs. Noise Filtration:** The 5 artificial booking noise columns collectively consumed **0.2244** of the Random Forest's structural importance. However, the statistical filter successfully isolated them, as all 5 noise features fell outside the Top 7 ranks and scored below the critical F-score threshold of 10.0 (while valid features scored above 30.0).



* **Feature Selection Sweep ($k$-table):** Validation F1 is 0.6988 for k=5, 0.8333 for k=7, 0.7857 for k=10, 0.8049 for k=12 and 0.7848 for all 17. k=7 is best: k=5 drops real signal columns, and larger k adds noise columns back.





* **Hyperparameter Hyper-Tuning Trade-offs:** Grid search (27 candidates, 135 fits, best cross-validated accuracy 0.8952) reached validation F1 0.7750; randomized search (9 candidates, 45 fits, 0.8905) reached 0.7848; the untuned forest on the same 7 columns reached 0.8333. So tuning did not beat the untuned forest on validation. The cross-validated accuracies differ by only 0.0047, and on a 180-row validation set with 42 delayed parcels one or two parcels move F1 by more than that, so these differences are within noise; the lesson is that tuning on a tiny validation set can chase luck, and that a default forest on well-chosen features is already close to the best this data supports. The final configuration is the default forest (`n_estimators` 100, no depth limit, `min_samples_leaf` 1) on k=7 features.





* **Alert Threshold & Operations Trade-off:** olds.csv`).\*\* The operations rule needs validation recall of at least 0.80. Threshold 0.6 gives recall 0.7619 (too low); threshold 0.5 gives recall 0.8333 with precision 0.7955 (TP 35, FP 9, FN 7); lowering to 0.4 raises recall to 0.8810 but precision falls to 0.7400, and at 0.1 precision is only 0.4824. The highest threshold meeting the rule is **0.5**.



* **Holdout Test Evaluation:** ored once).\*\* At threshold 0.5: TN 125, FP 14, FN 10, TP 31; accuracy 0.8667, precision 0.6889, recall 0.7561, F1 0.7209. Test recall (0.7561) is lower than validation recall (0.8333) and below the 0.80 target. With only 41 delayed parcels in the test set, 31 caught instead of the 34 that would give 0.83 is a small absolute difference, so it is partly sampling noise, but I do not claim the 0.80 recall target is met on unseen data.







## Operations recommendation





* **Escalate segment.** K-Means on the hub profiles (`hub_segments.csv`, `segment_profile.csv`) puts nine hubs in Escalate, with a segment delay rate of 0.4600, mean delivery 64.6504 hours, mean distance 470.4757 km and 84.3444 stops: Nagpur (0.46), Kochi (0.36), Patna (0.46), Ranchi (0.38), Guwahati (0.62), Raipur (0.48), Bhubaneswar (0.40), Siliguri (0.44) and Agartala (0.54). Watch has 8 hubs (delay rate 0.1550) and Standard 7 hubs (0.0257).



* **Tier labels that mislead\*\* (`tier_vs_segment_mismatch.csv`):

- Kolkata (Tier 1) behaves like a Watch hub, so the Tier 1 label overstates its reliability.

- Nagpur (Tier 2) and Kochi (Tier 2) behave like Escalate hubs, so the Tier 2 label understates their risk.

- Dehradun (Tier 3) behaves like a Watch hub, so the Tier 3 label is too pessimistic.

Operations should assign playbooks from the data-driven segment and treat the tier label as a static attribute only.



**Alert threshold** Flag a parcel when its delay probability is at least 0.5. On the test rows, about 7 of every 10 flagged parcels are really delayed (precision 0.6889) and about 8 of every 10 delayed parcels are caught (recall 0.7561, that is 7.6 of 10); the validation recall was 0.8333, so plan for roughly 75 to 83 percent.



**New parcels**Of the 48 new parcels in `new_shipment_actions.csv`, 8 are flagged; 6 of those sit in Escalate hubs and need a hub-manager escalation, and the other 2 get a proactive customer call. The remaining 40 need no action.



**Why K = 3** The across-to-within ratio (`part_d_separation.csv`) is 2.894 for K=2, 5.3928 for K=3, 6.3047 for K=4 and 6.8866 for K=5. The largest jump comes from 2 to 3 (+2.4988); after that it adds only +0.9119 and +0.5819. K=4 has cluster sizes 8-7-5-4 and K=5 has 8-7-4-3-2, so each contains a cluster of fewer than 6 hubs, too small to carry its own playbook, and the business runs exactly three playbooks. K=3 gives sizes 9-8-7 with clearly separated delay rates.













## Production plan



**(a) Production-readiness characteristics mapped to repository items**

- *Accuracy:* held-out validation and test metrics in `part_b_metrics.csv` and `part_c_final_test.csv`, with the blind baseline for comparison.

- *Reliability:* `clean_shipments` handles duplicates, casing, missing values, the 999 kg sentinel and the unknown payment mode; `predict_delay.py` asserts no missing feature values.

- *Reproducibility:* pinned `requirements.txt`, committed `generate_data.py`, fixed `random_state=42`, and the run order in "How to run".

- *Performance (speed):* the model scores a whole batch in one `predict_proba` call and the RandomForest with seven selected inputs is small enough to run inside the scoring script on demand.

- *Maintainability:* one shared module `src/shipment_prep.py`, one script per Part, and constants (`FEATURES`, `PROMISED_HOURS`) defined once.

- *Consistency:* training and prediction use the same `clean_shipments` and `build_features`, with the stored medians in `models/impute_values.csv` and the column order in `models/feature_order.csv`.

- *Monitorability:* `new_shipment_actions.csv` stores the delay probability, flag, segment and action for every parcel, so each can be compared with the real outcome later.



**(b) Quantities to monitor, with triggers**

1. Weekly delayed share of delivered parcels. The training share is 0.2317; investigate if a week is outside 0.17 to 0.29 for two weeks running.

2. Weekly share of parcels flagged. On the test rows 45 of 180 parcels (0.25) were flagged; investigate if the weekly flagged share leaves 0.15 to 0.35.

3. Recall on parcels whose outcome is now known, over a rolling four weeks with at least 40 delayed parcels. Test recall was 0.7561; retrain if it falls below 0.65.

4. Share of missing `distance_km` or `parcel_weight_kg` values in the incoming data. In the training export about 3 percent of distances (36 of 1,200) were missing; alert if a week exceeds 10 percent, since the median fill would then dominate.



**(c) Retraining and the sale window.** Retrain monthly on the latest delivered parcels and immediately if monitor 3 trips; refresh hub segments quarterly, because hub behaviour (for example Kolkata or Nagpur) changes slowly. The 15 to 28 September sale window (`sale_event_flag`) raises delivery times (the data adds hours for sale parcels and extra hours for Express during a sale), so delay and flag rates in that window must be compared with the same kind of event (the previous sale), never with ordinary weeks, or the monitors will fire falsely. Data drift here would look like a shift in the distance or stops distribution, a changed service-type mix (more Express), a growing share of missing values, new hubs that the model has never seen, or a hub moving to a different segment.









## Limitations



1. The data is synthetic: effects such as the sale-window delay and the four hubs that operate unlike their tier label were built into the generator, so real shipments will be messier and the scores here are likely optimistic.

2. The test set has only 41 delayed parcels, so test recall (0.7561) and precision (0.6889) carry wide uncertainty; a change of a few parcels moves them by several points.

3. The 0.5 threshold and the final configuration were chosen on one 180-row validation split (42 delayed parcels), and the three candidate configurations were within noise of each other, so another split could choose differently.

4. The regression winner (linear regression) and the model I recommend shipping (gradient boosting) differ; only the former was scored on the test rows.

5. The hub profiles and K-Means segments are computed from all 1,200 parcels (50 per hub, 24 hubs), so the segments are only as stable as these small samples, and K-Means results for K=4 and K=5 depend on the seed and hub order.

6. The packaged classifier is fitted on the 840 training rows only (not training plus validation), and the pickle depends on the exact scikit-learn version.
